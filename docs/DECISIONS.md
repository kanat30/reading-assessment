## [2026-07-24] The override recompute cutoff is aligned to the score-time engine (migration 0022)
- **Decision:** Ported `lib/scoring/metrics.ts::getLastReachedIndex`'s gap/tail rule into the SQL `recalculate_session_metrics` (migration `0022`, CREATE OR REPLACE + re-asserted internal-only grants + backfill of overridden sessions). The function no longer derives the reached cutoff as `MAX(voiced word_index)`; it now collects the ordered voiced indices and, on the first large silent gap (`>= 12` never-voiced words, `NOT_REACHED_GAP_THRESHOLD`) followed by only a sparse tail (`<= 3` voiced words, `NOT_REACHED_TAIL_TOLERANCE`), cuts at the end of the leading contiguous read — exactly as the score-time engine does. Closes the divergence flagged in the same-day tests decision below. Guarded by two new SQL scenarios (S10 stray-tail trimmed, S11 genuine-skip kept) that mirror the TS `getLastReachedIndex` tests.
- **Why:** The mismatch meant a stray-tail read (student stops, but the aligner attaches a lone match far ahead) scored correctly at score time yet silently re-inflated its denominator — dropping accuracy and nudging WCPM — the instant a teacher applied *any* word-level override. That is a narrower recurrence of the precise regression migration 0019 was written to eliminate, and it fires on the trust-building override flow, so it had to be closed before a validator sees the product. The recompute test suite's SQL↔TS parity contract is what surfaced it.
- **Alternatives considered:** Collapse both paths to a single source of truth by moving the override recompute out of plpgsql into a TS server action that calls the same `getLastReachedIndex` — architecturally cleaner (one implementation, no "keep in sync" hazard) but a materially larger change to a security-definer, RLS-guarded path, and unnecessary to fix the bug; deferred. Leave the SQL simpler and instead loosen the TS engine to also use MAX — rejected: the gap/tail trim is the *correct* behavior (it's what keeps a stray match from corrupting the score), so the fix is to make SQL match TS, not the reverse. Do nothing / document only — rejected: it's a real mis-score, not a cosmetic gap.
- **Multi-tenancy / RLS:** `recalculate_session_metrics` is a SECURITY DEFINER helper that bypasses RLS, so it is only safe while (a) no client role can call it directly and (b) its sole caller `apply_event_override` still enforces the caller's school (`auth.uid()` → teacher's `school_id`, rejecting a session that "belongs to a different school"; 0014/0018). 0022 re-asserts the internal-only grants (REVOKE from PUBLIC/anon/authenticated, GRANT to service_role) **and self-verifies against the live catalog at apply time** — a catalog-driven DO block (mirroring 0020) that aborts the whole migration atomically if the helper is not SECURITY DEFINER, has no pinned `search_path`, is executable by anon/authenticated, if the wrapper has lost SECURITY DEFINER or its per-school guard, or if RLS is disabled on `sessions`/`session_events`/`session_event_overrides`. The full-stack checks are gated on the wrapper's existence so the hermetic arithmetic harness is unaffected; the harness itself now includes a **tenancy stage** proving the guard passes on intact tenancy and *aborts* on a disabled-RLS or dropped-school-check regression. Live lockdown confirmed today independently (anon `POST /rest/v1/rpc/recalculate_session_metrics` → HTTP 401). No RLS policy is added, dropped, or weakened; tenant isolation is unchanged and now guarded as a tripwire.
- **Implications for the code:** The two thresholds now live in *two* places (`lib/scoring/metrics.ts` and migration 0022); both carry a reciprocal "keep in sync" comment, and any future tuning of the not-reached heuristic must edit both (or take the deferred single-source refactor). Normal reads are unaffected (no qualifying gap → still the last voiced word); only stray-tail reads change, and only overridden sessions ever execute this function, so the backfill repairs exactly the affected rows. **Not yet applied to the live DB** — 0022 needs a `db push`; until then production's overridden stray-tail sessions keep the old (inflated-denominator) recompute. Because the migration self-verifies tenancy at apply time, a `db push` into a DB whose tenancy guard had somehow regressed would abort rather than proceed.

## [2026-07-24] First automated tests cover the scoring trust linchpin (override recompute + score-time engine)
- **Decision:** Added the project's first automated test suites, both targeting the metric math the entire "trustworthy, teacher-overridable" pitch rests on. **(1)** A hermetic SQL harness (`scripts/test-recompute.sh` + `supabase/tests/{_setup,recompute_metrics.test}.sql`) that spins up a *throwaway* PostgreSQL cluster in a temp dir, loads the **real** `recalculate_session_metrics` verbatim from migration `0019` (no re-implementation, so it can't drift from production), runs 9 scenarios, and tears the cluster down — never touching a real DB and needing no running server. Scenarios cover every branch of the override count: baseline/not-reached cutoff, reject-error→correct, flag_error→self_correction, flag_error demoting a correct word, approve as no-op, latest-override-wins (the 0017 fix), override-past-cutoff ignored, nothing-voiced→zeros, and the WCPM-rate math. **(2)** A `node:test` suite (`lib/scoring/metrics.test.ts`, run via `tsx`) covering the score-time engine `getLastReachedIndex` (incl. the gap/tail stray-match logic) and `calculateMetrics`. Wired as `npm test` / `test:recompute` / `test:scoring`. No dependency added (Node's built-in test runner + existing `tsx`; `psql`/`initdb` from a local Postgres install).
- **Why:** `lib/scoring/` was flagged as the highest-value untested surface (STATUS), and the override recompute specifically is where the last three migrations (0017 self-corrections, 0018 tenancy, 0019 not-reached cutoff) each fixed a silent mis-score triggered by the very teacher-correction flow meant to build trust. Before a district validator sees this, "the recompute is correct" needed to become "the recompute is *provably* correct under each override action" — a regression here is a credibility failure, not a cosmetic bug.
- **Alternatives considered:** Port the SQL logic to TS and test the port — rejected: it would test a re-implementation, not the function that runs in production, and would not catch SQL/TS divergence (the 0017 bug class). Run the suite against the live/local Supabase DB — rejected: not hermetic, mutates real rows, needs secrets/network. Add a heavyweight test framework (Jest/Vitest) — unnecessary; Node's built-in runner + `tsx` cover it with zero new deps. Load all 21 migrations into the throwaway cluster — rejected as fragile (Supabase-isms: `auth`, storage, RLS roles); instead the harness creates a minimal role shim + the exact columns the function reads and loads only the real `0019` function body.
- **Known divergence surfaced (not yet closed):** the SQL cutoff (`MAX(word_index) WHERE spoken_word IS NOT NULL`) is *simpler* than TS `getLastReachedIndex`, which additionally cuts an earlier stray tail after a large silent gap (`NOT_REACHED_GAP_THRESHOLD`/`TAIL_TOLERANCE`). They agree on normal reads (the parity fixture asserts identical numbers on both sides) but can differ on a stray-tail read: after an override, the SQL recompute would count up to the stray match where the score-time engine excluded it — a residual, narrower instance of the exact bug 0019 targeted. Left as a documented follow-up (align the SQL cutoff to the gap/tail rule, or collapse both to one source) rather than silently "fixing" it here.
- **Implications for the code:** `npm test` is now a pre-commit/CI gate for scoring changes; the shared expected values across the two suites (correct=5, total=7, wcpm=5, acc=71 on the common fixture) are the SQL↔TS parity contract — changing counting on either side breaks one suite. The SQL harness requires a local Postgres (`initdb`/`psql`; Homebrew `postgresql@16`/`@14` auto-detected); `test:scoring` has no such dependency. Suite is arithmetic-only: the tenancy/school-check wrapping (`apply_event_override`, `auth.uid()`) is out of scope here (covered by the migrations' own self-verification). No app/schema change, no migration.

## [2026-07-14] The dashboard groups a student's multi-passage assessment into one row
- **Decision:** On the teacher dashboard, the sessions of one student's multi-passage (median-of-3) assessment now collapse into a single grouped row instead of appearing as three independent readings. Grouping is purely a display concern in `app/dashboard/client.tsx`: `buildDashboardRows()` keys sessions by `(assessment_id, student_id)` and groups only when the assessment is multi-passage (`assessments.passage_ids.length > 1`); single-passage and legacy assessments render exactly as before. The group header shows the student, `class · Level N · K passages · median X WCPM`, a "R of K" badge, and a K-segment progress indicator (filled = passage read) in the waveform slot. Expanding shows a compact **overall median-of-3 report** (`components/report/GroupMedianReport.tsx`) followed by one expandable per-passage sub-report — each sub-row reuses the existing session-row markup (`renderSessionRow`), so per-passage status/notes/delete/override all still work. The overall report is derived entirely from the submitted passages' stored `scores_json`: the **median WCPM + Hasbrouck–Tindal benchmark band** (via the existing `calculateMedianResult` + `BenchmarkBand`), where the benchmark ribbon carries a **numbered marker (1/2/3) per passage at its own WCPM** with the median marker highlighted in accent-blue (`BenchmarkBand` gained an optional `passageMarkers` prop; the single-passage report is unchanged), plus supporting **median accuracy**, **typical (median) prosody level**, and **aggregate comprehension** across the passages, and an advisory-only note linking `/explainability`. Only the outer card header labels the median (the earlier duplicate `MedianScoreSummary` "Median Score" heading was dropped). Median is computed client-side over the passages actually scored (`medianWcpm`), so partial completion (1 or 2 of 3 read) is shown honestly (a "Partial — R of K read" flag) rather than hidden.
- **Why:** The median-of-3 protocol (DECISIONS 2026-07-11) fans one assessment out to three library passages, and each read is a separate `sessions` row, so a single student produced three dashboard entries with three different passage titles — visually indistinguishable from three unrelated assessments and, at class scale, a mess. Grouping makes the unit of assessment (the student's benchmark, whose headline number is the *median* of the three) legible at a glance and surfaces partial reads ("2 of 3") explicitly, which matters because students on constrained Chromebooks may stop before all three. Kept deliberately simple per the request — no new aggregate report construct, no cross-student analytics (out of scope per PRODUCT.md).
- **Alternatives considered:** A server-side aggregate/materialized "assessment result" row (heavier, duplicates the median already derivable at read time, and would need its own status/override model — rejected as over-engineering for a display grouping); grouping in the SQL query (the realtime/polling paths would each need to re-group, and the filters operate per session — client-side grouping over the already-filtered list keeps one code path); rendering the three passages as a flat indented list without a collapsing header (less clear that the median is the headline, and doesn't reduce the row count the teacher scans).
- **Implications for the code:** Grouping runs over `filteredSessions`, so class/date/status/notes filters still act per session; a status filter that hides some passages of a group will make its "R of K" reflect only the visible sessions (the total K still comes from `passage_ids.length`) — acceptable for the common no-status-filter case. Both live-update queries (realtime single-fetch and the 15s polling fallback) and the server load in `page.tsx` now select `passage_index` + `assessments.{reading_level, assessment_period, passage_ids}`; any new session-fetch path feeding the dashboard must select these or its multi-passage rows won't group. Group expansion uses a separate `expandedGroupKey` state (keys are prefixed `g:`/`s:` so they never collide with session UUIDs); passage sub-reports reuse `expandedSessionId`. The overall report needs `scores_json.{metrics, prosody, comprehension}` (already fully selected by the dashboard) and the assessment's `reading_level`/`assessment_period`; the band falls back to a plain median-WCPM line if either is missing/invalid (guards against legacy multi-passage rows). Because the band = `calculateBenchmark(medianWcpm, …)` and the median WCPM equals one of the three actual passage WCPMs (for 3 read), it stays consistent with each passage's own report. Display-only, no DB migration, no scoring change, no new API/RPC. The standalone report page (`/report/[id]`) still shows one passage at a time — reusing `GroupMedianReport` there is a natural follow-up but was intentionally out of scope here.

## [2026-07-14] Comprehension grading is decoupled from the student's submit (background AI call)
- **Decision:** `POST /api/comprehension` no longer blocks the student's "Submit answers" on the Claude grading call. It now persists the **raw** answers synchronously (into `comprehension_answers` for legacy passages, and a pending `scores_json.comprehension = { status: "grading", score: 0, total, answers }` marker for both), returns immediately, and runs `gradeComprehension` in the background via Vercel `waitUntil`. When the model returns, the background task overwrites the marker with the real `{ score, total, answers }` and upserts the graded per-answer rows. The teacher report shows "Grading…" for the brief window the marker is pending (`SessionReport.tsx`).
- **Why:** The student was waiting 10–30s on "Submitting…" for a single passage — the entire duration of a synchronous Claude call whose output **only the teacher ever sees**. The student flow never reads the grade (the submit handler only checks `response.ok`; the done page shows nothing about comprehension), so the wait was pure dead time on constrained Chromebooks — exactly the flaky-network, low-patience context PRODUCT.md flags. Grading is advisory and already teacher-overridable/re-gradable, so it does not need to be on the student's critical path.
- **Alternatives considered:** Fire-and-forget from the client (don't await the POST) — rejected: navigating away can kill the in-flight serverless request on a Chromebook, losing the answers; server-side `waitUntil` guarantees completion after the response. Lazy grading on first teacher report-open — viable and cheapest (no wasted grade if never viewed) but pushes latency onto the teacher and complicates the report load; `waitUntil` keeps grading automatic. Streaming/faster model — treats the symptom, not the coupling. Keeping the batched single-call grade (already optimized from N calls, see `comprehension.ts`) — still 10–30s of variance/cold-start on the student's path.
- **Implications for the code:** Raw answers are now written **before** grades exist, so any consumer of `comprehension_answers` or `scores_json.comprehension` must tolerate an ungraded/pending state (`status` null on rows; `comprehension.status === "grading"` in scores_json). The pending marker also serves as the idempotency guard (the existing `existingScores?.comprehension` check blocks duplicate submits). If the background grade fails, the marker + raw answers persist and a teacher re-grade recovers it — **note the pre-existing gap that `/api/comprehension/regrade` only handles legacy DB passages, not library passages**, so a failed library-passage grade currently has no teacher-driven recovery (grading itself has an internal fallback and rarely throws; worth closing when the regrade path is generalized). No DB migration (the pending marker reuses the nullable `status` and the existing `scores_json` shape).

## [2026-07-14] A repeated word at the stop point must not teleport the read forward
- **Decision:** The stop point (how far the student got in the 60-second sample, per DECISIONS 2026-07-11) is made robust against the alignment attaching a stray match past where the student actually stopped. Two coordinated deterministic fixes, no LLM: **(A)** the Needleman–Wunsch traceback in `lib/scoring/alignment.ts` now applies an *earliest-match bias* — when a diagonal MATCH ties with skipping the expected word (an omission), it prefers the omission, so a repeated spoken word attaches to its **earliest** passage occurrence and the read stays contiguous; **(B)** `getLastReachedIndex()` in `lib/scoring/metrics.ts` no longer returns the max voiced index but the end of the *leading contiguous read* — it cuts at the first large silent gap (`NOT_REACHED_GAP_THRESHOLD = 12` never-voiced words) that is followed by only a sparse tail (`NOT_REACHED_TAIL_TOLERANCE = 3`) of voiced words, treating that tail as a stray post-stop match. A genuine mid-passage skip (a big gap the student then reads substantially past) is left intact and still counts as omissions. Guarded by `scripts/validate-stop-point.ts`.
- **Why:** A student read up to the first "construction" in "…before construction could begin" and stopped; the app reported the stop point at a *later* recurrence of "construction", marking the whole intervening paragraph as read-but-omitted and corrupting WCPM, accuracy, and the benchmark band. Root cause: global NW alignment forces every trailing (unread) passage word to a gap regardless, so attaching the last spoken word to the earlier vs. later copy of a repeated word scores **equally** — and the old traceback checked the diagonal (match) first, biasing ties toward the **highest** passage index (the later copy). A nastier variant: common words in the skipped remainder ("the", "before", "could") can make the forward jump score *strictly higher*, so a tie-break alone is insufficient — hence the stop-point guard (B) in addition to the aligner fix (A). This is the exact "ASR/alignment error masquerading as a student reading error" failure the strategy docs flag as the highest-risk, trust-destroying variable.
- **Alternatives considered:** Tie-break only (A) — cleanest, but misses the coincidental-common-word case where the later alignment scores higher, not equal; stop-point guard only (B) — fixes the score and band but leaves the transcript highlighting the *wrong* "construction" as the read word (the first is shown unread), because the spoken word is still attached to the later index; semi-global / free-end-gap alignment — the theoretically tidy model for "read a prefix", but a larger rewrite of the scoring core that doesn't by itself resolve the earlier-vs-later repeated-token ambiguity; cutting the read at *any* large silent gap — simpler, but under-counts a genuine skipped line the student reads past (rejected per the product decision to keep real skips as omissions).
- **Implications for the code:** `getLastReachedIndex()` remains the single source of the cutoff — `metrics.ts`, `patterns.ts`, `SessionReport.tsx`, `SyncedTranscript.tsx`, and `PrintReport.tsx` all derive from it, so both fixes propagate to scoring, error counts, patterns, and the transcript/print display at once. The two thresholds are the tuning surface if future passages need it. Fix is score-time only: existing sessions keep their stored events/scores until re-scored (no migration); the aligner change only affects newly scored reads. Ties into WER validation — worth including a repeated-word-stop sample in the pre-demo set.

## [2026-07-14] `assessments.passage_id` is nullable; a CHECK guarantees a passage source
- **Decision:** Dropped the legacy `NOT NULL` on `assessments.passage_id` (migration `0021`) so passage-library assessments — which reference 1–3 library passage IDs via `passage_ids[]` and have no row in the `passages` table — can be created with `passage_id = NULL`. In its place added a stricter, format-agnostic CHECK `assessments_has_passage_source` = `passage_id IS NOT NULL OR cardinality(passage_ids) > 0`, so the DB still guarantees every assessment carries *a* passage source. Applied to the live DB 2026-07-14.
- **Why:** `passage_id` was declared `NOT NULL` in `0001`, when every assessment pointed at a single `passages` row. `0016` added the passage library but never relaxed that constraint, so the dashboard's library create path (`app/dashboard/client.tsx`, which inserts `passage_id: null`) failed for **every** library assessment — single- or multi-passage — with a 400 (`null value in column passage_id ... violates not-null constraint`). The bug surfaced as "can't create a 3-passage assessment" but was not multi-passage-specific. Verified against the live DB before writing the migration: PostgREST OpenAPI confirmed `passage_id` was NOT NULL, all 15 existing rows had a non-null `passage_id` (so the new CHECK held for every row with no backfill), and the lone existing library row succeeded only because it *also* carried a legacy `passage_id`. Verified after apply: `passage_id` no longer appears in the table's `required` set.
- **Alternatives considered:** Application-only enforcement of "at least one passage source" (leaves the DB able to hold an orphan assessment with no passage — rejected; the CHECK makes the invariant a hard guarantee); backfilling library rows with a synthetic legacy `passages` row (reintroduces the duplication the library was meant to remove); making the code write a fallback legacy `passage_id` for library assessments (what the one pre-existing library row accidentally did — masks the model split and breaks median-of-3 passage resolution per DECISIONS 2026-07-11).
- **Multi-tenancy / RLS:** Unaffected. Tenant isolation on `assessments` is the `school_id` policy set from `0002` (`current_teacher_school_id()`); none reference `passage_id`, and `0021` touches no RLS. The `passage_id → passages(id) ON DELETE RESTRICT` FK is preserved (a NULL FK is simply unenforced), so legacy single-passage rows keep referential integrity. The CHECK is data-integrity only, tenant-agnostic, and idempotent (guarded via `pg_constraint`).

## [2026-07-13] The teacher report is teacher-only; students never read session data
- **Decision:** Removed all anonymous RLS read access to `sessions`, `session_events`, `comprehension_answers`, and `students` (migration `0020`). The comprehension page's passage/questions lookup — previously the reason those anon policies existed — now goes through a bounded `GET /api/comprehension` (admin client, validated by the assessment `share_token` + the same 2-hour post-reading window as the submit path). The student-facing "view report" link was also removed from the done page. `/report/[id]` is now reachable only by an authenticated teacher of the session's school, via the existing 0002 school-scoped policies.
- **Why:** `0006`→`0012` had granted `anon` SELECT on those four tables for any session created within 30 days, to power a student-facing report link. That exposed the full report — WCPM, the At/Below/Well-Below benchmark band, the synced transcript, prosody, the AI summary, and the student's name — to anyone holding a session UUID, for 30 days. It was inconsistent with the biometric gating on `/api/audio/[id]` (audio locked, but the report wrapped around it open — DECISIONS 2026-07-10) and with the product decision that students don't view reports. On shared Chromebooks a Back-button press was enough to surface the prior student's band + name — the exact placement/surveillance risk PRODUCT.md and the DOE AI guidance warn against.
- **Alternatives considered:** Narrowing the anon window from 30 days to the 2-hour active window and dropping only the students/events/answers reads (lighter, but the scored report stays briefly anon-readable — rejected as a half-measure); keeping the anon `sessions` SELECT but restricting columns (Postgres RLS is row- not column-level, so it can't hide `scores_json`); a public view exposing only passage-routing fields (more surface than a bounded API route).
- **Implications for the code:** The student flow now needs **zero** anonymous read access to `sessions` — only anon session INSERT (0002) and the service-role scoring/comprehension pipelines remain. ## [2026-07-11] Words never reached in the 60-second sample are "not reached," not errors
- **Decision:** Because the read is a fixed 60-second timed sample (see the entry below), a student normally stops partway through the passage. Every passage word after the last one they actually voiced is treated as **not reached** — excluded from WCPM, accuracy, error patterns, the report's error counts, and the transcript's error styling. It is never counted or shown as an omission error. The cutoff is derived, not stored: `getLastReachedIndex()` in `lib/scoring/metrics.ts` returns the highest `word_index` that was voiced (`spoken_word !== null`); everything past it is not reached. A mid-passage skip (an omission with voiced words after it) is a genuine error and stays counted — only the trailing never-voiced run is dropped. In the transcript the reached portion renders normally and the remainder collapses behind a marker ("reached N of M words · K not read · show"), muted and non-interactive when expanded (`components/SyncedTranscript.tsx`).
- **Why:** The Needleman–Wunsch alignment emits one event per expected word, so it classified the entire unread tail as `omission`. WCPM/accuracy were already correct (the JS engine scored only up to the last attempted word), but three things were wrong: (1) the transcript rendered ~150+ trailing words in error-red, (2) the error legend counted them — e.g. a Level-4 wolves read showed "Error (172)" when only 9 errors (6 substitutions + 3 real omissions) were inside the 122 words actually reached, and (3) the suggested error patterns were flooded with the tail. There was also a **latent scoring bug**: the DB recompute (`recalculate_session_metrics`, migrations 0014/0017) counted every non-insertion event as a word attempted, so the first teacher word-override would recompute accuracy over the whole passage (e.g. 122/285 ≈ 43% instead of the true 86%) — a trust-breaking regression triggered by the override flow itself. Migration 0019 derives the same cutoff in SQL (`MAX(word_index) WHERE spoken_word IS NOT NULL`) and excludes the tail from both counts. Verified against the live DB (management token expired, so introspected via PostgREST + behavioral RPC): the referenced columns exist with the expected types; across all 2,626 live events `spoken_word IS NOT NULL` ⇔ `start_timestamp_ms IS NOT NULL` with zero exceptions (the cutoff is unambiguous); and the function's tenancy posture is intact — `anon` gets `42501 permission denied`, `service_role` reaches the body, matching the 0017 hardening. 0019 keeps `SECURITY DEFINER` + pinned `search_path` + client-role EXECUTE revoked, touches no RLS policy, and leaves the school-checking wrapper functions (`apply_event_override`/`delete_event_override`) unchanged.
- **Alternatives considered:** Storing an explicit `not_reached` event type (self-describing, but needs a CHECK-constraint migration, a data backfill of every existing session's trailing events, and touches the override RPCs — the derived-cutoff approach fixes existing sessions with zero data migration); hiding the unread remainder entirely (loses the how-far-did-they-get context a teacher wants — the collapsed marker keeps it); hard-truncating the passage text before alignment at an estimated word budget (guesses the cutoff instead of measuring where the reader actually stopped).
- **Implications for the code:** `getLastReachedIndex()` is the one source of the cutoff — scoring (`metrics.ts`, `patterns.ts`), the report counts (`SessionReport.tsx`), and the transcript (`SyncedTranscript.tsx`) all derive from it; new consumers must too, rather than treating trailing omissions as errors. Existing sessions' stored `error_patterns` (a score-time artifact) remain inflated until re-run via `scripts/backfill-patterns.ts` — its skip-if-already-enhanced filter must be relaxed to re-process them. Migration 0019 needs `db push` to take effect; until then the override-recompute path keeps the old denominator (initial scores are unaffected).

## [2026-07-11] The student read is a fixed 60-second timed sample, auto-stopped by the app
- **Decision:** Each passage read is capped at 60 seconds and the app auto-stops the recording and advances when the limit is reached, rather than running until the student taps stop. The student-facing timer is a calm depleting bar (no ticking numbers) with a subtle "Almost done" cue in the final 10s; a manual stop remains for students who finish the passage early. Constant `READ_TIME_LIMIT_SECONDS` in `app/read/[token]/recording/page.tsx`.
- **Why:** WCPM is computed as `(correctWords / durationSeconds) * 60` (`lib/scoring/metrics.ts`) and scored against Hasbrouck–Tindal norms, which are calibrated on a strict 60-second sample. An open-ended read (e.g. a 3-minute halting reading extrapolated to a per-minute rate) is not comparable to those norm tables and moves the band unpredictably. The one-minute read is also the DIBELS/Acadience protocol the product mirrors. A visible count-up clock was judged anxiety-inducing for middle-schoolers, hence the numberless bar.
- **Alternatives considered:** 90s/120s windows (more words, but no longer a standardized 60s sample — weakens norm comparability); teacher-configurable limit (adds scope and a way to silently break comparability — deferred); no visible timer at all (calmest, but the auto-stop feels abrupt with no warning).
- **Implications for the code:** Passages must be long enough that a typical reader does not finish inside 60s (see ROADMAP "Passage fixes"). The auto-stop is a render-scoped `useEffect` guarded on `state === "recording"` so it closes over fresh state; `handleStop` is idempotent. If the cap ever becomes configurable, the `durationSeconds` sent to scoring must still reflect the actual capped read.
